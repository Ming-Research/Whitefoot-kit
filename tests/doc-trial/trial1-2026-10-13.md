# Whitefoot writing-guide trial

The new guide improved progress over the baseline: **5/15 cases passed within eight rounds**, versus none in the baseline. **None passed within three rounds.** Most early failures contradict rules already stated in the guide. The main needs are a whole-program audit workflow, clearer examples at type and ownership boundaries, and explicit disclosure of the kernel’s postcondition limits.

The first three rounds contain **44 compiler diagnostics and one runtime failure**, not 45 compiler rejections.

## 2. Canonical-formatting stalls

There are **20 FORM-2 diagnostics** across all eight rounds. They concern three exact rules:

| Cases/rounds | Violated canonical rule | Diagnostic |
|---|---|---|
| 01 r3; 04 r5; 09 r3; 10 r2; 15 r3 | Struct-destructuring `let_stmt` renders completely on one line | `expected: ""`, `found: "\n    "` |
| 01 r4–8; 02 r4–7; 09 r2; 13 r4–7 | No blank line inside a top-level item | `expected: "\n  "`, `found: "\n\n  "` |
| 13 r3 | Exactly one empty line between top-level constants; alias exception does not apply | `expected: "\n\n"`, `found: "\n"` |

The compiler repeatedly exposed **different existing violations**, rather than rejecting an unchanged marked location.

- **01:** after collapsing `Inputs`, each subsequent round deletes one internal blank line. R5 says, “I need to remove the extra blank line”; its edit uses `replace_all: false`. The attempt still reaches another blank-line error at r8.
- **02:** r5 explicitly quotes “no blank line inside an item”. R6 says, “I need to remove all extra blank lines inside the function,” but edits only selected clusters. R8 finally sweeps the remaining gaps.
- **13:** after fixing constant separators, four body gaps cost four more rounds. R6 says, “Another extra blank line in the function body. Let me remove it.”
- **09:** removing all internal blank lines exposes a separate multiline-destructuring violation.

The guide’s recovery instruction—**“Fix the first error and check again”**—fits the observed local repair habit. The canonical rules themselves are correct and were delivered.

**Single guide change:**

> “After a rejection, audit every file for the same rule before resubmitting. For FORM-2, keep every ordinary/destructuring statement on one physical line, remove every internal blank line, and check all top-level separators.”

**Single compiler feature:** attach a **complete suggested canonical-byte diff** to the first FORM-2 rejection, using the already-derived forest. Keep the specified primary error and do not rewrite or accept normalized input. This would expose all formatting repairs together without abandoning FORM-1/2’s rejection policy.

## 4. Case 12: runtime failures in rounds 3–5

The atomic updates are correctly grouped. The failure is **completion ordering**, not lost increments.

| Round | Bug and observed result |
|---|---|
| **3** | Expression-statement spawns belong to `main`’s activation. Counter is observed before its exit join; status **1**, empty output. Joining during exit does not reevaluate the already-computed failure. |
| **4** | Each spawn becomes `let rN = spawn ...` inside a `for` body. Each bound child joins at that iteration’s block end. The first producer fills the eight-slot queue and waits before any consumer starts; status **124**. |
| **5** | Counter children remain bound and finish sequentially. Producers/consumers again use expression spawns in `main`; total is observed before their join; status **2**. |
| **6** | All activities launch inside synchronously called `run_activities`. Its return joins the children; `main` observes afterward. **Pass.** |

R4’s runtime message is:

> `whitefoot completion: every context waits for a guard or for another context, and no host operation is outstanding`

The guide **does address this exact problem**, and case 12 read it. Its concurrency section includes a launcher-helper example, states both join rules, and warns about intermediate coherent observations. Haiku recognized one rule at a time but failed to combine them. A short warning about **bound spawns inside loop bodies** would make the dangerous scope concrete.

## 6. New Whitefoot diagnostic findings

The baseline already identifies first-error-only staging, lexical priority, escaped FORM-2 bytes, missing infix-flattening hints and uppercase names reported at `_`. The following findings add new evidence:

1. **Incorrect effect-root explanation — 05 r3, 09 r5.** The diagnostic says “every effect path is rooted at one formal value parameter … this root is not one”, although `value` is a formal parameter. The rule requires a **reference parameter**. Identify the by-value mode and instruct removal of its entry.

2. **Rust array types do not receive a type-form repair — 03 r1–3.** The expected-token list never supplies `Array<T,N>`. Haiku moves the invalid type between contexts and then deletes the required storage. This differs from the baseline’s array-*literal* findings.

3. **Operation-domain and propagation errors lack explanations — 08 r2/r3/r8.** `InvalidOperation` should show the permitted conversion endpoint or float comparison form. `InvalidPropagation` should show operand Result type, enclosing `ExitStatus`, and the required enclosing Result boundary.

4. **Contract advice hides an unsupported result boundary — 07 r2–3.** Suggesting a callee postcondition does not expose that its custom enum has no admitted route. The subsequent “expected `)`” only reveals the one-field grammar restriction, not the separate FN-9 limitation.

5. **Aggregate ownership repairs omit their capability cause — 11 r2.** “Write `move p`” is locally correct but led to moving all Results. Show the instantiated type and the noncopy payload that requires the move.

6. **Reference-kind mismatches omit available repairs — 11 r3, 15 r5, 14 r4.** Array-versus-slice errors can suggest a range reference. Reference-derived match payload errors can identify the payload’s origin and suggest `val^` for copy referents.

7. **Deadlock diagnostics omit guard and join locations — 12 r4.** The runtime accurately describes global nonprogress, but not the producer’s full-queue guard and parent’s implicit loop-body join. Those locations would explain why consumers never launch.

8. **`give if` receives a lexical-looking FORM-3 error — 14 r3.** The useful explanation is contextual: conditional values initialize `let` only.

The semantic diagnostics that already give **exact effect rows, conflicting declaration locations, residual linear obligations, and unproved/refuted goals** materially help recovery. The trial supports extending that specificity to operation domains, ownership capability causes, reference kinds and implicit joins.
